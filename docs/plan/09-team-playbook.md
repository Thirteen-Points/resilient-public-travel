# 09 · 咱们仨怎么干活（大白话版协作手册）

> 这份文档不讲术语，专门回答三个问题：
> **① GitHub 上怎么配合？② 每个阶段各人要交出什么？③ 出事了找谁？**
> 其他文档（00–08）是"详细规则书"，这份是"上手说明书"。冲突时以规则书为准，日常干活看这份就够了。

---

## 一、第一次设置（30 分钟，做一次就够）

咱们仓库已经建好了，现在还差这几步。**谁做：C 带着大家做一遍，一次学会。**

1. **把本地的 `docs/plan/` 和 `contracts/` 推上去**——这是咱们的计划书和数据格式约定，所有人都以 GitHub 上这份为准。
2. **保护 main 分支**（重要，5 分钟）：
   网页打开仓库 → Settings → Branches → Add branch rule → 分支名填 `main` → 勾上 "Require a pull request before merging"（需要 1 个人同意才能合并）→ 保存。
   这样就没人能"手滑"直接改坏主分支。
3. **每人建一个自己的分支**（分支 = 你自己的草稿纸）：
   - A 用 `feat/a-frontend`
   - B 用 `feat/b-events`
   - C 用 `feat/c-engine`
4. **建一块任务看板**：仓库页 → Projects → New project（Board 看板模式）。
   建 5 列：`待办 / 本周做 / 正在做 / 待检查 / 完成`。
   然后 B 把 77 张任务卡抄成 Issues（一张卡一个 Issue，标题写 `[T3.5] 候选生成` 这样）。这是 B 第 1 周的任务之一。
5. **每人装一个 GitHub Desktop**（桌面版，图形界面，不用背命令行）。新手优先用它。

## 二、每天怎么配合（就这一套动作，形成肌肉记忆）

**核心原则一句话：`main` 分支是"正式版"，永远保持能跑；每个人在自己的分支上画草稿，画完请别人看一眼，没问题再合进正式版。**

每天的循环就五步：

```
1. 开工前：先"拉取"（Pull）—— 把别人昨天的成果同步下来
2. 确认自己在自己的分支上（别在 main 上直接改！）
3. 干活，干完"提交"（Commit）—— 提交说明写清楚干了啥
4. "推送"（Push）到自己的分支
5. 网页上发 Pull Request（PR，意思是"请检查我的草稿"），@一个人帮你看
```

**关于 PR 的三条规矩：**

- **看的人 24 小时内处理**：要么点合并（Merge），要么留言说哪里要改。不许装没看见。
- **一次合并别贪多**：一天的工作量一个 PR 就够了。攒一周再合并 = 冲突地狱。
- **提交说明有格式**：`[任务号] 干了什么`，比如 `[T6.2] 地图画出六个站`。方便以后回头找。

**改冲突了怎么办（一定会遇到，别慌）：**
GitHub 说 "Conflict" = 你俩改了同一个文件的同一处。**别自己瞎选**，在群里喊一声"谁动过 XX 文件"，两个人一起看，留下对的版本，再合并。10 分钟的事。

**每天晚上 9 点，群里发三句话（雷打不动）：**

```
昨天完成：xxx
今天要做：xxx
卡在哪：xxx（没卡就写"无"）
```

这 30 秒的事，能避免 90% 的"我以为你在做"。

## 三、每周怎么配合（两个固定节目）

| 时间 | 节目 | 干什么 |
|---|---|---|
| **每周三晚**（线上就行，1 小时） | **合体夜** | 三个人把各自的分支都合进 main，当场把接口对上。今天专修"合不拢"的问题，不写新功能。 |
| **每周日下午**（1 小时） | **合体测试 + 录屏** | 按当周目标，把网站从头到尾点一遍，录屏存档。然后 15 分钟复盘：这周哪里顺、哪里卡、下周砍不砍东西。 |

录屏很重要：**它就是每周的"进度证明"**，10/4 中期作业和最终视频直接从这里面剪。

## 四、每阶段各人交什么（重点看这里）

28 天 = 4 周。每周末的"合体测试"就是验收时刻，下面写的就是**验收时要亲眼看到的东西**。

### 第 1 周（9/21–9/27）：把地基打好 —— "各干各的，周末能拼起来"

| 人 | 这周交出什么（说人话版） |
|---|---|
| **A** | 网页能打开，**地图上能看到六个站和所有线路**，能画 800 米圈。用假数据就行（种子数据已经在 `contracts/seed/` 里，直接用，**不用等后端**）。路线卡片的样子先画出来（里面数字可以是假的）。 |
| **B** | **"收到一条消息 → 自动变成一张事件卡"这个流程跑通**。先用最笨的关键词匹配就行，AI 后面再接。另外把三张假事件卡（低/中/高置信度）准备好，把 77 张任务卡抄进 GitHub Issues。 |
| **C** | **线路数据表整理好**：哪些线路真实存在、班次几分钟一班、票价多少、能装多少人，每条都写明出处（真实/推算/模拟）。再写个小程序：给它起点终点和时间，它能吐出几条走法。 |

**9/24（周四）晚有个硬deadline：三个人把"数据长什么样"的约定定死并冻结。** 就是把 `contracts/` 过一遍，都点头。之后谁想改格式，必须三个人都同意。**这事儿不定，后面三周的活全是白干。**
周中还有两个小deadline：C 在 9/22 晚前把线路数据给 A，B 在 9/23 晚前把事件卡给 A——都是为了 A 不用等别人。

**周日验收**：地图有站有线路、事件卡能显示三档置信度、输入起终点能出几条走法（丑没关系，**能跑就行**）。

### 第 2 周（9/28–10/4）：打通一条完整链 + 交中期作业 —— "先跑通，再好看"

**这周的头等大事：把这条链从头到尾串起来——**
有人报告故障 → 变成事件卡 → 管理员点"发布" → **地图上那段线路变色** → 路线自动重算 → 卡片刷新。
允许丑，不允许断。这条链是咱们的命根子，优先级高于一切。

| 人 | 这周交出什么 |
|---|---|
| **A** | 地图变色 + 路线卡片完整版（有打分条、预计时间**区间**、风险提示、数据来源徽标）。 |
| **B** | AI 接入（文本变事件卡），置信度会随多个来源慢慢上涨（0.2 → 0.55 → 0.9），管理员审核流程能用。 |
| **C** | 算路引擎出**真结果**（不用假数据了），把网站部署上网（申请免费服务器，配一个网址）。 |

**10/4（周日）交中期作业**，要交这几样（A 主导打包，大家把材料给 A）：
1. 仓库链接 + 一份**英文** README（说明这是什么、怎么跑起来）
2. 一个能访问的网址
3. **3 分钟演示视频**（就从每周录屏里剪）
4. 一页进度报告：做完了什么 / 在做什么 / 下一步 / 卡点

### 第 3 周（10/5–10/11）：把三个亮点做达标 —— "从'做出来了'到'做成了'"

咱们对外就讲三句话：**早发现、懂个人、会分流**。这周的目标是让这三件事**经得起当场测试**：

| 亮点 | 验收时要亲眼看到的画面 |
|---|---|
| **早发现** | 一条文本进来，30 秒内变事件卡；置信度从 20% 涨到 90% 能看见；点发布后 5 秒内地图变色。 |
| **懂个人** | 同一场故障，**"赶时间的上班族"和"坐轮椅的用户"看到的首选路线不一样**，而且各自能说出为什么。轮椅用户的路线里绝不能出现小巴。 |
| **会分流** | 1 万人仿真跑出**真数字**（不是文档里的占位数）：不引导大家挤一条线 vs 引导分流，对比图摆出来，**运力缺口多少也如实摆出来**。 |

| 人 | 这周交出什么 |
|---|---|
| **A** | 两个画像的对比页面 + 分流结果的大屏看板（柱状图一摆，外行 10 秒看懂）。 |
| **B** | "一句话变偏好"功能（用户打"我腿脚不便别让我走太多路"，系统自动调整推荐），置信度动画串进时间线。 |
| **C** | 1 万人仿真的**真实数字** + 分流比例算法 + 保证发布事件后 5 秒内重算完成。 |

**周日（10/11）验收最严格的一次**：三个亮点逐条测，测不过的当场决定砍还是改说法（先砍花哨的，命根子不动）。

### 第 4 周（10/12–10/18）：只修不加，彩排，交作业 —— "别再想新点子了"

- **10/14（周三）功能冻结**：之后只许修 bug，谁提新功能就写进"以后再说"清单。
- 三个人互相找茬：**A 去砸 C 的引擎**（乱输起终点看会不会崩），**B 去砸 A 的界面**（用最难的方式操作），**C 去砸 B 的审核流**（投矛盾信息看看置信度掉不掉）。
- **彩排 3 次**，其中一次专门演练"出事故"：拔网线、关掉 AI、重启后端——演示当天什么都可能发生。
- 交的东西：最终版网址 + PPT（英文）+ 3 分钟视频（带字幕）+ 问答清单（评委可能问的 16 个问题，提前背）+ 一个"离线备份包"（U 盘里有视频和录屏，网崩了就放视频）。

**10/18（周日）：交作业。收工。**

## 五、铁律（就四条，都记不住就别干别的了）

1. **main 永远能跑。** 谁合坏了谁修，修不好喊人。
2. **卡住 2 小时必须喊人。** 这是规矩不是丢脸。三个人一起看 10 分钟往往就通了，自己闷头耗一晚上才是真浪费。
3. **不偷偷加功能。** 想到好点子 → 写进"以后再说"清单 → 继续干手里的活。咱们的工时只够做"必做"清单，加一个就得砍一个（砍什么见 `06` 文档的砍单表）。
4. **每个数字标真假。** 真实的、推算的、模拟的，三级标注，一个都不能含糊。答辩时"你这数据哪来的"是必考题。

## 六、出事了找谁

| 情况 | 找谁 |
|---|---|
| 界面/地图/卡片坏了 | A |
| 事件卡/置信度/审核/AI 的问题 | B |
| 算路结果不对/数据可疑/网站打不开 | C |
| 不知道某数据是真是假 | C 整理、B 复核（台账在 `data/PROVENANCE.md`） |
| 想改数据格式 | 三个人都同意，走 PR |
| 意见吵起来了 | 看数据；没数据就 A 拍板，记下理由，不翻旧账 |
| 某人这两天有事 | 提前说，备份人顶上（A↔B、B↔C、C↔B 互为备份） |

## 七、一句话总结

> **白天各画各的草稿（分支），晚上 9 点群里报三句，周三合体对接口，周日合体测一遍 + 录屏。每周交付一样"能亲眼看到"的东西：第一周看得见地图，第二周整条链能跑通，第三周三个亮点扛得住测，第四周交作业。卡住 2 小时喊人，绝不偷偷加功能。**
