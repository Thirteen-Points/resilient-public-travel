# 04 分工与任务卡（Workstreams, Owners & Tasks）

> 原始分工只有三句话（A 做看得见的、B 做耳朵+守门员、C 做大脑+腿）。本文把它拆成 **10 条工作流 / 77 张任务卡**，每张都有负责人、备份人、产出、完成定义（DoD）、难度与工时。
> **难度：⭐ 新手可独立完成 ｜ ⭐⭐ 需要一点经验 ｜ ⭐⭐⭐ 需要踩坑与调试。工时单位：小时。**

---

## 1. 分工原则（先立规矩，再分任务）

| 原则 | 说明 |
|---|---|
| **一人一条主工作流** | 每人有 1 个"主战场"和 1 个"次要战场"，避免三人都做同一件事 |
| **每张卡都有备份人** | 唯一负责人是项目最大的风险。备份人不做，但要知道怎么接手（看文档 + 能跑起来） |
| **接口人制度** | 每个模块有一个"对外接口人"，别人只找他，不直接改他的文件 |
| **⭐ 任务优先给新手** | 标 ⭐ 的任务技能门槛低（改数据、写文案、画组件、核数据），照文档就能做 |
| **按真实工时取舍（重要）** | 77 张卡全部实现约 **360 人时**（含联调、彩排、文档）；4 周实际可支配约 **200–240 人时**（3 人 × 每周 17–20 h 的冲刺强度）。**结论：必须砍掉约三分之一** —— 砍单规则与"绝不砍清单"见 `06` §3，「必做」目标集 ≈ **210 人时**。若某周实际投入低于 15 h/人，直接按 `06` §3 顺序砍 |
| **每周一次"反向测试"** | 每周日演示前，每个人测试**别人**的模块（换视角才发现问题） |

### B —「系统的耳朵 + 守门员」｜主战场：事件管道 ｜次要：画像服务与内容

| 项 | 内容 |

## 4. 协作机制（不照做就会打架）

### 4.1 固定节奏

| 时间 | 事项 | 时长 | 产出 |
|---|---|---|---|
| 每天 21:00 | 群里三行状态：**昨天完成 / 今天要做 / 卡在哪** | 5 min | 无阻塞过夜 |
| 每周三晚 | **集成夜**：三方把分支合到 `main`，一起修接口 | 60–90 min | `main` 可跑 |
| 每周日晚 | **Demo dry-run**：按 `07` 脚本走一遍，录屏留档 | 30 min | 当周视频 |
| 每周日晚 | 风险登记册更新 + 下周排期 | 15 min | `06` 更新 |

### 4.2 Git 与看板

- 分支：`main`（永远可跑）｜`feat/a-map-layers`｜`feat/b-event-pipeline`｜`feat/c-engine`
- **禁止直接 push `main`**；PR 需 1 人 review；PR 描述写"改了哪个契约字段/影响了谁"。
- 看板列：`Backlog / Todo / Doing / Review / Done / Blocked`；每张卡对应 `04` 里的任务 ID，**卡上不写 ID 一律打回**。
- 提交信息格式：`[T3.5] 候选生成支持多样性约束`。

### 4.3 接口交接物（每个人必须准时交给别人的东西）

| 从 | 给 | 交接物 | 截止 |
|---|---|---|---|
| C | A | `contracts/seed/network.seed.json`（可用坐标与站序） | **9/22 晚** |
| B | A | `contracts/seed/event.seed.json`（三态事件卡） | **9/23 晚** |

| C | A | `SimResult` 真实数字（替换占位值） | 10/8 |

### 4.4 每周"反向测试"

每周日 dry-run 前，**打乱顺序**互测：A 测 C 的引擎（随便输一个 OD 看结果是否合理）、B 测 A 的界面（挑最难的路径走）、C 测 B 的审核流（用一条矛盾信息看置信度是否下降）。**测试结果记进看板 `Blocked` 列。**
