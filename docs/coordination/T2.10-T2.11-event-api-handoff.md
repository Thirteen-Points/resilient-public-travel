# B 的事件 API、审核与 SSE 交接

本交接针对 `Mingquan-Xia` 分支上的 B 后端。启动服务前设置环境变量 `REVIEW_API_TOKEN` 为仅审核方/受信后端持有的随机值；未设置时事件写入、审核和待审订阅会拒绝请求，原始 Signal 上报仍可进入收件箱。不要把令牌放入前端源码或 Git。

## 最小流程

1. `POST /api/signals` 接收用户原文，返回 `signal_id`，但**不会自动发布**。
2. 受信后端携带 `X-Review-Token` 调用 `POST /api/events/ingest`，正文为 `{"signal_id":"..."}`。若无可靠匹配，返回 `state=needs_review` 和结构化草稿，不会猜严重度或运力数字。
3. 审核方确认草稿和交通数字后，携令牌向 `POST /api/events` 传入完整、`status=pending_review`、`version=1`、仅有一条已存储 Signal 的 Event。服务端重新计算置信度，不能用请求中的分数伪造权威来源。
4. 后续同一事件的 Signal 再经 `/api/events/ingest`，会合并到唯一匹配卡片，版本和审计日志各递增一次；匹配模糊时返回 409，交人工处理。
5. `POST /api/events/{id}/review` 携令牌，正文如 `{"action":"approve","actor":"admin"}`。动作支持 `approve`、`edit`（另传 `edits`）、`reject`、`expire`；非法转移返回 409，非法修改返回 422。低于 0.60 的卡片不能发布；审核加 0.05 后达到门槛才可发布。
6. `GET /api/events/published` 面向地图与路线引擎，仅返回已发布事件。`GET /api/events`、`GET /api/events/{id}` 是带令牌的审核视图。
7. `GET /api/stream/events` 携令牌订阅 SSE。每帧的 `event` 是最新完整事件，`change` 是对应的审计动作及当时置信度；`id` 是可重连的审计序号。重连时传 `Last-Event-ID` 或 `after_id`。前端若用浏览器原生 `EventSource`，它不能发送自定义令牌头；应由受信后端代理，或用可带头的流式 `fetch`，**不要把令牌放 URL**。

## 边界与待对接

- 当前仓库没有 C 的真实 LLM 客户端，因此默认走 T2.7 离线规则；`create_app(llm_client=...)` 已留适配入口。真实模型的 T2.6 样本验收仍需另做。
- 创建首张完整 Event 需要人工提供严重度、区段运力因子等确定值；服务端不会根据自由文本杜撰交通数字。未能可靠匹配的报告仍在 Signal 收件箱中，不会自动成卡。
- SSE 展示 B 的事件更新；A 的界面接入与 C 的发布后图快照/路线重算仍是跨团队联调事项，不属于这次 B 的实现。
- 目前审核令牌是单一服务端共享令牌，适合受控演示环境；正式公网开放前应接入团队身份验证和细粒度权限。
