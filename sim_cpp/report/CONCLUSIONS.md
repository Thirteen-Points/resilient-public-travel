# CONCLUSIONS — 东铁 10,000 人沙盒

> 只写本沙盒在给定输入/假设下能支持的结论；不外推到真实世界或全网。

## 5–6 条分析型结论

1. **物理运力不是本场景的约束，规划 cap 才是。** 三组 denied 都是 0，峰值列车载客率只有 A 23.8%、B 36.2%、C 34.8%，远低于 95%；真正绑定的是 3,400/460 的 bucket 规划 cap。任何“95% 上限导致拒载/崩溃”的叙事都与本实验不符。
2. **封闭把网络压成一条快速轨道绕行，bucket 无法真正分散 14:00 后的需求。** KOT→EXC 在封闭期间只有 KTL+TWL+ERL 一条快速可行路线；KTL bucket 3,400/h 满后，窗口 1 的 420 人（合计 686 人 fallback）回到同一条路线。B 的路线 HHI 0.406 低于 C 的 0.500，但这主要来自少量 KTL+TML / ERL+TML / BUS_182 分流，而不是把 5,000+ 人均匀摊开。
3. **protected-first 是有效的尾部保险。** B 的 forced alight 为 0，C 为 633；轮椅 P95 从 60 min 降到 17，长者从 29 降到 17；B 的 protected assigned 为 4000，protected fallback 为 0。代价是普通群体平均延误高 0.85–0.99 min、P95 高 7 min。这不是 Pareto 改进，而是分配选择。
4. **B 的总体平均只低 0.13 min，不能称为“更快”。** B 的平均延误 9.37 min，C 为 9.50 min；B 的 P95 反而高 1 min（18 vs 17），affected 比例更高（58.8% vs 57.0%）。B 改善的是最坏尾部（max 30 vs 60，>30/>45 为 0），不是整体分布。
5. **bucket 的容量副作用会制造新的峰值。** KTL bucket 满后，71 名普通乘客被分到 BUS_182（+13 min），把 B 的峰值车辆载客率推到 54.6%（71/130），并产生 B 的 30 min 最大延误；C 的峰值只有 34.8%。所以“把需求从大车挪到小车”不一定改善集中度，可能只是把峰值搬到小车上。
6. **B 的优势高度依赖计划性封闭的先验知识。** B 预知 14:00–15:00 关闭，C 不预知；B 能在 13:52–14:00 把 633 名风险乘客提前改道，C 只能让他们在 HUH 被强制下车。若封闭突发、B 也只能在 14:00 才知道，B 的 forced=0 和最大延误优势会大幅缩小。这是本实验最重要的 external-validity 限制。

## 4 个最亮眼数据

1. **forced alight：B 0，C 633。** C 的 633 人中轮椅 127、长者 106；B 通过提前分流把这一类事件清零。
2. **最大到达延误：B 30 min，C 60 min。** C 的最大值来自 127 名轮椅在 HUH 等到 15:00；B 的最大值来自 71 名被分到 BUS_182 的普通乘客。两者的“最坏”不是同一群人，这正是分配政策的差别。
3. **站台等待：B 58253 人·分，C 65375 人·分；HUH 单项 B 2488 vs C 9370。** B 把 HUH 的封闭期负担转移到 KTL/TWL/ADM 和少量 bus，HUH 人·分降到 C 的约 27%。
4. **bucket 账本：9314 assigned / 686 fallback / 4000 protected；1929 人撞到 route cap，231 人撞到 segment cap；71 人分到 bus。** 在 3,400/h 规划 cap 下 bucket 确实绑定，但物理列车只有 36.2% 峰值；这组数字把“规划容量”和“物理容量”的差别暴露得最清楚。

## 能说 / 不能说

### 能说

- 在本沙盒的输入、seed、10,000 人、13:00–15:00、ERL HUH–EXC 14:00–15:00 关闭、95% 每车上限、3,400/460 bucket 规划 cap、protected-first、15 min 公平上限等假设下，B 与 C 的上述差异是**可复算的仿真结果**。
- B 的 forced alight 为 0，C 为 633；B 的最大延误 30 min，C 为 60 min；B 的轮椅 P95 17 min，C 为 60 min。这些是本运行的数字，不是估计。
- bucket 的 3,400/460 规划 cap 确实绑定；686 人 fallback；71 人被分到 BUS_182；峰值车辆载客率 54.6%。这些都可以从 `B/bucket_allocations.csv` 逐行复算。
- 本场景的 denied 为 0，95% 物理上限没有绑定；任何关于“拒载压力”的结论都不应从这里得出。
- 自测、验证、确定性均 PASS：输入 SHA256、10,000 行、站台事件积分、延误配对、bucket 账本、两次运行哈希。

### 不能说

- **不能说 bucket 在真实故障下一定更好。** B 预知计划性封闭，C 不预知；这不是同一信息集。若封闭突发，B 无法提前分流 13:52–14:00 的 633 名风险乘客，结论会变。
- **不能说 bucket 是 Pareto 改进。** 普通群体平均延误高 0.85–0.99 min、P95 高 7 min；B 的总体均值只低 0.13 min，不能包装成“所有人都更快”。
- **不能说 95% 上限安全或危险。** 本场景峰值只有 36.2%，denied=0；这不代表真实高峰或背景客流下不会拒载。
- **不能说轮椅乘客在真实 HUH 一定被困。** C 的 127 名轮椅等到 15:00，是本模型“400 m 步行上限 + 所有巴士未确认低地板”的结果；现实中可能有电梯、低地板巴士、工作人员协助等未建模因素。
- **不能说这是个性化/water-filling。** bucket 是按小时窗口的静态 protected-first 分配，没有个体化定价、没有实时反馈、没有 water-filling；不要把这些词贴到本实验上。
- **不能说这是官方预测或全网结论。** 单 OD、无背景客流、无晚高峰、无返程、无 dwell/bunching、无天气/电梯故障；10,000 人、一个 seed、一个故障窗口，不能外推到全网全天。
- **不能说 3,400/460 是实测容量。** 它是 repo 的 route supply planning cap（合同/规划口径），不是运营实测；换一个 cap，B 的分配和峰值会变。
