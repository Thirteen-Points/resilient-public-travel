# Simulation data

`*.input.json` files are **simulated-only** algorithm fixtures. The matching
result JSON is generated by `scripts/precompute_sim.py`; headline benefits are
never typed into the result by hand. The current M2 input baseline and its
field-by-field source classifications are recorded in
[`m2-input-manifest.json`](m2-input-manifest.json).

The manifest distinguishes three things: values copied from C-Data, model or
scenario assumptions, and references that are not yet wired into the runtime
input. A source reference alone does not upgrade a fixture value's provenance.
In particular, the checked-in M0 route supply is not calculated from
`data/network/lines.json` or `data/capacity_method.md`; it remains simulated.
Current capacity inputs are estimates or unverified, and no verified operator
capacity, residual load, or passenger-demand feed is connected. Do not present
these simulation results as measured passenger flows or verified operating
capacity.

Capacity semantics:

- `service_capacity_per_hour = 3600 / headway_s * vehicle_capacity * available_capacity_factor`
- `capacity_per_hour = service_capacity_per_hour * eta_max_factor`
- standard users stop at `capacity_per_hour`; protected users may use remaining
  physical capacity when no fair alternative exists, and that target overload
  remains visible in the result;
- queue utilisation uses `service_capacity_per_hour`, preserving the physical
  headroom created by the 0.85 target.

All demand, OD weights, persona shares, route-supply values, route residual-
capacity factors and simulation outcomes in the current scenario are
`simulated`. No fixture value is promoted to `real` or `real-derived` by this
manifest. The route adapter consumes the existing `RouteCandidate` fields
without modifying their names or meaning. To create a data-backed scenario,
the producer must explicitly construct the input through
`backend.app.sim.adapters.routes_from_contract`, preserve per-field provenance,
and resolve the known gaps listed in the manifest.

The multi-OD M0 path uses
`backend/tests/fixtures/multi_od_routes.simulated.json`. Its 30 OD entries
reference compact simulated candidate profiles; they are not verified routes
and are never duplicated to reach the target of ten candidates per OD.
Per-OD candidate shortages and unmet demand are written to
`m0-multi-od-verification.json`, outside the frozen public `SimResult`.

Run from the repository root with the bundled/runtime Python:

```text
python scripts/precompute_sim.py
python scripts/verify_sim_m0.py
python scripts/verify_sim_multi_od_m0.py
python -m unittest discover -s tests -v
```

The M0 verifier writes `m0-verification.json`. A PASS means only that the
deterministic simulation and adapters are internally consistent against
simulated fixtures; it is not transport-data verification.

The M2 six-station multi-OD scenario is generated separately:

```text
python scripts/precompute_sim_m2.py
```

It queries the current seed-backed C-Route engine for all 30 directed OD pairs
and writes `m2-route-input.json`, `m2-simulation-result.json`, and the CSV/Markdown
comparison. The checked-in result records the seed, input hashes and query
coverage. All inputs remain simulated. The P3 version of this generator also
projects the seed's directed line segments into explicit shared capacity
resources. Previously checked-in M2 artifacts are retained as historical
evidence; they do not automatically acquire the newer model's semantics.

The P3 comparison uses the same frozen M2 input so route/population changes
cannot explain the difference:

```text
python scripts/precompute_sim_p3.py
```

`p3-shared-capacity-report.md` and `p3-shared-capacity-evidence.json` record the
old result, current model, complete resource inputs and a deliberately
constrained 10% residual-capacity sensitivity run. The normal 10,000-person,
30-OD run is computed twice and must produce identical results. Capacities
are passengers per hour on each directed segment, floored over the scenario
window; one passenger consumes one place on every traversed segment.

The two scenario files can be fetched through the existing result endpoint:

```text
/api/sim/result?scenario_id=m2_six_station_directed_od_am_peak_p3_shared_segments
/api/sim/result?scenario_id=m2_six_station_directed_od_am_peak_p3_shared_segments_residual_10pct
```

Both policies use the same protected-first physical boarding evaluation.
Guided chooses each person's highest-ranked feasible route rather than filling
the largest route bucket regardless of preference. Accessibility and extra
travel of at most 15 minutes remain hard filters. That limit does not promise
that queue waits or unserved passengers' waits stay below 15 minutes.

No operator residual occupancy, dedicated wheelchair berth throughput,
train-by-train seat propagation or inter-window queue carryover is verified.
Queue delay uses the maximum route/segment bottleneck estimate to avoid adding
overlapping waits. Zero unmet demand remains a property of simulated inputs,
not evidence of real-world capacity. The 10% factor is explicitly synthetic.

The aggregate `/api/sim/load` accepts optional private `shared_resources`
metadata (`resource_id`, `route_ids`, `service_capacity_per_hour`, `headway_s`,
`target_factor`, `provenance`) without changing frozen public response fields.
Repeated identical route supplies are counted once; conflicting duplicates
fail. With no explicit resource input, it cannot infer partial overlaps from
route IDs alone. Runtime integration can project a pinned graph using
`sim.shared_capacity.resources_from_snapshot(snapshot, route_details, depart_at)`;
route/graph revision mismatches fail rather than applying stale capacity.
